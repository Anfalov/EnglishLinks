# Реестр источников и порядок обновления

Единый машинный реестр: [`data/source-registry.json`](../data/source-registry.json).
Он хранится в архиве проекта вместе с исходными выгрузками и сборщиками.
Текущий срез соответствует EnglishLinks 0.4.2 (наборы имён сохранены из 0.4.0). Файлы исходников не скачивались
повторно при составлении реестра.

Для всех исторических скачиваний точное время неизвестно. В JSON это
`retrieved_at: null`; известная дата отдельно записана в `retrieved_date`.
Часовой пояс прежних дат не зафиксирован, поэтому они не пересчитываются.
`registered_at` — фактическое время внесения записи в реестр, НЕ время скачивания.
Время файла, загрузки в чат, коммита или публикации релиза не подставляется
вместо времени выгрузки.

У каждого снимка есть точный URL, локальный путь, SHA-256 и размер в байтах.
Для репозиториев сохранён полный SHA коммита, для PetScout — версия, file ID,
адрес ZIP, хеш ZIP и путь внутри архива. Для валют сохранены отдельные URL.
Таким образом, отсутствие старого времени не мешает определить точные байты.

## Что фиксировать при каждом новом скачивании

1. Источник, точный URL, язык, редакцию игры и исходную сборку, если она указана.
2. Версию релиза, file ID или полный commit. Если версия отсутствует — `null`,
   а не предполагаемый номер текущей игры.
3. `retrieval_started_at` и `retrieved_at` с датой, временем и часовым поясом
   в ISO 8601. Предпочтительно UTC с `Z`; для чтения можно показывать UTC+05:00.
   `retrieved_at` фиксировать после успешного получения исходных байтов.
4. SHA-256, размер, путь сохранённого файла. Для извлечённых файлов также
   сохранить данные родительского ZIP; время распаковки не является скачиванием.
5. Для вручную выписанных веб-данных сохранить URL и время чтения каждой страницы,
   заявленную на ней сборку и способ извлечения. Сами записи снабдить SHA-256.

Новые снимки добавлять в историю `snapshots` с новым уникальным `id`.
Старые исходники сначала переносить в архив снимков и обновлять их пути в реестре,
чтобы замена рабочего файла не уничтожала историю. Ошибку скачивания записывать
отдельно: она не является новой успешной выгрузкой и не заменяет прежний снимок.
Текущий реестр составлен вручную из существующих manifests; прежние сборщики
не заполняют время получения автоматически. Обновление реестра — обязательный
шаг обновления данных.

## Порядок обновления после релиза WoW

1. Зафиксировать целевую сборку Forever и собрать новые снимки в отдельную папку.
   Сохранить сведения о скачивании сразу, до пересборки.
2. Проверить заголовки/схемы, локаль, хеши, дубликаты ID и изменения названий.
   Отсутствие записей в новой выгрузке не считать автоматическим удалением из игры.
3. Обновить рабочие manifests и общий реестр. Сверить лицензии изменённых источников.
4. Пересобрать item, typed, quest и supplement-пакеты. Приоритеты и нормализация:
   [QUEST-SOURCES.md](QUEST-SOURCES.md), [SUPPLEMENT-SOURCES.md](SUPPLEMENT-SOURCES.md).
5. Проверить отчёты конфликтов, покрытие и несколько новых/изменённых ID.
   Выполнить тесты и проверить ссылки в игре. Сохранить результат как новую версию
   архива проекта, вместе с реестром и исходниками.

Важное ограничение существующих сборщиков: `build_supplements.py` и часть проверок
пока привязаны к 70124, PetScout 69913 и текущим числам записей. При новом релизе
нужно явно обновить эти ограничения по проверенным источникам. Одной замены
номера сборки в имени файла недостаточно. Старые источники нельзя помечать новой
сборкой только потому, что обновился клиент.

Наблюдения форматов ссылок пользователя: `data/link-observations.json`.
Они хранятся отдельно от источников английских названий.
