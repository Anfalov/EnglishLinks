# Автоматические выпуски

## Разработка и выпуск

Рабочая ветка — **`develop`**. Все изменения, включая документацию, исправления
и обновления баз, сначала сохраняются в ней. Push в `develop` не запускает
release workflow и не создаёт новую версию. Тестовый ZIP можно собрать локально:
`python tools/package_release.py`.

**`main` предназначен для выпусков.** Проверенные изменения переносятся из
`develop` в `main` по запросу на выпуск или перенос в `main`. Обычный запрос
сохранить изменения в GitHub означает push в `develop`. После выпуска работа
продолжается в `develop`, синхронизированной с `main`.

Правила для работы с репозиторием закреплены в [AGENTS.md](../AGENTS.md).

## Сборка и публикация

Push в `main` запускает **Build and release addon** только при изменениях
в `EnglishLinks/`. Push с одной документацией или исходными данными не создаёт релиз. Вручную его можно
запустить через Actions → Build and release addon → Run workflow (ветка main).

1. Выставляется версия в TOC, Lua и метаданных выпуска.
2. Готовые файлы аддона упаковываются в один установочный ZIP.
3. ZIP сохраняется в Artifacts запуска (90 дней).
4. Создаётся тег `v<версия>` и GitHub Release с этим ZIP.

Выпуск не скачивает источники, не пересобирает словари и не сверяет их
с исходными базами. Тесты выполняются при разработке и в отдельном обновляторе
[Update addon names](AUTO-UPDATE.md). Упаковщик проверяет только структуру
установочных файлов и согласованность версии TOC/Lua.

Для установки нужен **EnglishLinks-<версия>.zip**. Он содержит только папку
`EnglishLinks`: runtime-файлы, значок и обязательные лицензии/уведомления.
README, исходные снимки и комплект автора не включаются. Отдельный файл
контрольных сумм не публикуется; SHA-256 самого asset доступен в GitHub.
Автоматические архивы Source code на странице Release — исходники проекта,
а не установочный пакет. После GitHub Release готовый ZIP отправляет
отдельный job через Upload API.

## CurseForge

После успешного GitHub Release отдельный job `Upload release ZIP to CurseForge`
скачивает именно опубликованный ZIP и отправляет его через Upload API.
Архив не пересобирается. `.pkgmeta` и отдельные правила исключения не нужны;
состав файлов по-прежнему задаётся только `tools/package_release.py`.

Настройка перед первым выпуском:

1. В GitHub → Settings → Webhooks отключить или удалить упаковочный вебхук CurseForge.
2. В CurseForge → Source → Automatic Packaging отключить упаковку и сохранить.
   Ссылку Repository URL на GitHub оставить.
3. В GitHub → Settings → Secrets and variables → Actions → New repository secret
   добавить `CF_API_TOKEN` со значением API-токена CurseForge владельца проекта.
   Токен не отправлять в чат и не добавлять в репозиторий.

ID проекта `1721401` взят из предоставленного пользователем URL страницы
CurseForge и записан в `publishing/curseforge/metadata.json`. В `game_version_source`
указаны канал Blizzard `product: wow_classic_beta` и регион `region: eu`.
Перед каждой отправкой скрипт читает публичную таблицу
`https://us.version.battle.net/v2/products/<product>/versions`, выбирает строку
EU и берёт первые три компонента `VersionsName`: например, `1.60.1.70205`
становится `gameVersionNames: ["1.60.1"]`. Полная сборка выводится в журнал.
Запрос списка версий CurseForge не выполняется; токен CurseForge не передаётся
Blizzard. Тип файла — Release.

Перед запуском игры нужно проверить и заменить `game_version_source.product`
на актуальный канал Forever. Код для смены канала редактировать не требуется.
При недоступности Blizzard, отсутствии региона или неверном ответе отправка
останавливается, без подстановки старой версии. TOC и сам ZIP не изменяются.
Если CurseForge ещё не знает новую версию, ошибку вернёт Upload API.
Changelog содержит секцию текущей версии из `publishing/curseforge/CHANGELOG.md`;
при автоматическом выпуске без такой секции используется короткая отметка об
обслуживании и обновлении базы названий. Успешная загрузка печатает ID файла
в журнал и summary Actions; модерация и окончательная публикация остаются на стороне CurseForge.

Без секрета job загрузки завершается понятной ошибкой, готовый GitHub Release
остаётся доступен. После устранения причины использовать **Re-run failed jobs**:
повторяется только загрузка, номер версии не меняется. Не перезапускать успешную
загрузку через Re-run all jobs: в этой интеграции нет защиты от повторной отправки
уже принятого файла.
При таймауте/неоднозначном ответе сначала проверить Files на CurseForge — файл
мог быть принят. Автоматических повторов POST нет.

Проверка без токена и загрузки файла (выполняет только GET версии Blizzard):
`python tools/upload_curseforge.py --version 1.0.0 --zip dist/EnglishLinks-1.0.0.zip --dry-run`.
Настройка начинает работать после переноса workflow в `main` и следующего выпуска.

Документация: [CurseForge Upload API](https://support.curseforge.com/support/solutions/articles/9000197321-curseforge-upload-api).

## Нумерация

Настройки находятся в `.github/release-version.json`. Сейчас версия вычисляется
как `1.0.(GITHUB_RUN_NUMBER - 6)`: запуск № 6 — **1.0.0**, следующий — **1.0.1**.
Номер запуска выдаёт GitHub; повторный запуск через **Re-run jobs** сохраняет
номер. Неудачный запуск может оставить пропуск в нумерации.

Это нумерация запусков одного workflow: не удаляй и не создавай его заново
для сброса счётчика. Чтобы начать другую линию с версии x.y.0, установи
`base_version` в `x.y.0`, а `run_number_offset` — в номер следующего запуска.
Этот запуск выпустит x.y.0, следующий — x.y.1. Существующие теги никогда не перезаписываются.

В исходниках `main` остаётся базовая версия. Версия конкретного выпуска сохраняется
в отдельном коммите под его тегом: его родитель — точный коммит, вызвавший запуск.
Автоматика не коммитит обратно в `main`, поэтому не создаёт циклов и не мешает
обычным пушам. Каждый push с изменениями аддона получает отдельную сборку; параллельные запуски
не делят номер версии. Номер в `/el status`, TOC и ZIP совпадает.

## Повторный запуск и права

Если публикация прервалась после создания тега, **Re-run jobs** собирает уже
помеченный коммит, загружает файлы и завершает тот же Release. Черновик Release
публикуется только после загрузки всех файлов. Чужой тег с таким номером
приведёт к ошибке вместо перезаписи.

Достаточно штатного `GITHUB_TOKEN` с `contents: write`, указанного в workflow.
Для GitHub Release дополнительные secrets не нужны. Для CurseForge нужен
отдельный секрет `CF_API_TOKEN` (см. выше). Если политика GitHub
запретит создание тегов или Releases, ZIP останется в Artifacts успешного шага
сборки, а ошибка публикации будет видна в журнале Actions.

Версии GitHub Actions закреплены по SHA. Для тестов используется `lupa==2.6`.

## Выпуск после автообновления

Обновлятор независимо запускается кнопкой или расписанием. После принятого
изменения имён он вызывает этот workflow с `source_sha`: это точный коммит
обновления, а не случайный более поздний HEAD. Коммит должен принадлежать `main`.
Причина явного вызова — push от `GITHUB_TOKEN` сам не запускает другие workflows.
Нумерация остаётся общей: используется счётчик **release.yml**, а не обновлятора.
