# Обновление названий

Рабочая база — `EnglishLinks/NameData.lua`. Аддон загружает один готовый словарь:
дополнительные пакеты не объединяются в игре.

## Запуск

В GitHub: **Actions → Update addon names → Run workflow**, ветка `main`.
`dry_run` проверяет источники и возможные изменения без push и выпуска.

Расписание — **понедельник и четверг, 09:00 по Екатеринбургу** (`04:00 UTC`,
cron `0 4 * * 1,4`). GitHub может
задержать старт. Этот workflow (`update-names.yml`, **u2**) не запускается от push.
Но релиз после push с изменениями `EnglishLinks/` в `main` тоже обновляет имена:
он вызывает общий `prepare-names.yml` (**u1**) перед упаковкой. Push в `develop`
по-прежнему ничего не публикует.

`u1` доступен только через `workflow_call`, а не отдельной кнопкой. Он принимает
`source_sha` и `dry_run`, возвращает `changed` и итоговый `source_sha`.
При ручном выборе ветки, отличной от `main`, задача пропускается.
`dry_run` применяет данные и запускает проверки в окружении Actions, но не
создаёт коммит, не обновляет ветки и не вызывает релиз.

Локально, Python 3.10+ и `lupa==2.6`:

```sh
# Только отчёт; аддон не меняется.
python tools/update_names.py
# Принять изменения локально; Git не затрагивается.
python tools/update_names.py --apply
```

## Правила объединения

1. Прочитать текущий словарь из файла аддона.
2. Скачать Wowhead Forever. Добавить отсутствующие ID, заменить изменившиеся
   названия. Списки, ограниченные числом строк, разбить по диапазонам ID.
3. Скачать закреплённые по текущим SHA файлы QuestieDB, EverythingQuests,
   Completao и ElliotWood/Forever, валюты TheWoWDB и PetScout Forever.
4. Недоступные или не прошедшие разбор источники пропустить с записью причины.
5. Дополнительные источники только добавляют отсутствующие ID. Несовпадающее
   название уже существующего ID остаётся прежним. Ничего не удаляется.

Если два ответа Wowhead одновременно дают разные имена одному ID, этот ID
сохраняет текущую подпись. Неименованные `rand` не добавляются. Полученный код
источников никогда не исполняется: импортёры извлекают только данные.

Файл Lua сериализуется детерминированно из результата объединения. Физически
он записывается целиком **только при изменении данных**, но логически меняются
только добавленные или переименованные записи. Удалённых ID нет. Время проверки
не записывается в файл аддона, поэтому повторная проверка не создаёт ложный релиз.

## Публикация

При изменениях автоматизация запускает тесты, сохраняет прежнюю базу, сырые
ответы, URL, SHA-256, время скачивания и список изменений в `data/auto-updates/`.
Коммит сначала отправляется в служебную ветку **`autoupdate`**, затем в `main`.
Нет изменений — нет коммита; отчёт всё равно доступен в Artifacts (30 дней).
Для u2 это также означает отсутствие релиза. Для релиза после переноса кода
из `develop` отсутствие новых имён не мешает выпуску кода.

`autoupdate` принадлежит автоматике и может обновляться с `force-with-lease`.
Не веди там ручную разработку. `main` обновляется только fast-forward:
перед публикацией повторно проверяется исходный SHA, а обычный push защищает
от изменения ветки между проверкой и отправкой. Если `main` изменился, подготовка
останавливается; при отсутствии новых имён актуальность SHA тоже проверяется.
Общая группа `englishlinks-name-preparation` не позволяет двум задачам u1
одновременно готовить и публиковать обновления. Она не охватывает вызывающий
workflow или релиз, поэтому вложенного ожидания той же блокировки нет.
GitHub хранит только одну ожидающую задачу в группе: при нескольких ожидающих
старую может заменить новая. Это не очередь всех запусков.

Для устаревшего релизного запуска нужен новый ручной запуск release от текущего
`main`: Re-run сохраняет старый `github.sha`. Обновлятор u2 без заданного SHA
при новой подготовке выбирает текущий `main`. Независимая работа в `develop`
не перезаписывается; если расхождений нет, эта ветка синхронизируется автоматически.

Встроенный `GITHUB_TOKEN` не запускает push-workflow своим push. Поэтому после
успешного переноса обновлятор вызывает **Build and release addon** через
`workflow_dispatch`, передавая точный SHA и **`update_names=false`**. Так релиз
не скачивает имена второй раз, а его собственный счётчик версий сохраняется.
Дополнительные secrets для вызова не требуются.
Если вызов выпуска не удался после push, запусти выпуск вручную с SHA коммита
из `autoupdate` и выключенным `update_names`.

При обычном релизе u1 не вызывает другой release: текущий release ждёт результат
u1 и собирает именно возвращённый SHA. Его исходный `github.sha` автоматически
не меняется при коммите обновлятора, поэтому передача SHA обязательна.

Повтор той же подготовки ищет в `main` уже опубликованный коммит по точному
`Update-Run-ID`, а для релизного запуска — также его тег с `Release-Run-ID`.
Если результат найден, используются прежние данные без нового скачивания.
Это позволяет продолжить после сбоя между push, созданием тега и публикацией.
Отчёт повторно не создаётся при использовании сохранённого результата.
Повторять успешный u2 целиком не нужно: он снова отправит запрос на релиз;
для восстановления выпуска используй уже созданный запуск release.

PetScout: страница файлов CurseForge определяет последнюю версию. ZIP скачивается
напрямую с ForgeCDN по опубликованному имени файла; адрес `/download/.../file`
не используется. Проверяются формат ZIP, размер и содержимое `data/locations.lua`.
Если список файлов или новая версия недоступны, пробуется известный архив из
manifest с проверкой SHA-256. Отчёт помечает его `pinned-fallback`: это загрузка
резервной версии, а не подтверждение отсутствия обновлений.

Wago и проверки по QuestV2 удалены. Сборку игры для загрузки указывать не нужно.

## Проверки и выпуск разделены

Тесты обновлятора проверяют приоритеты, пропуски источников, сохранение ID,
повторный запуск без изменений, загрузку готовой базы в Lua и работу ссылок.
Тесты работают с готовой базой и парсерами используемых источников.

Подготовка имён и упаковка — отдельные задачи. Release по умолчанию сначала
вызывает u1; сама задача упаковки выставляет версию и собирает готовый аддон,
не скачивая источники и не сверяя базу со старыми снимками. При
`update_names=false` подготовка пропускается. Ошибка u1 блокирует выпуск;
недоступный отдельный источник остаётся пропуском в отчёте по прежним правилам.
